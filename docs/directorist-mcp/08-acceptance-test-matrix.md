# Directorist MCP — Acceptance Test Matrix

Status: **release matrix scenarios remain Not run unless individually recorded with evidence**. Focused original-core and order/extension tests are documented in the [implementation verification record](../../docs/mcp/verification.md); they do not certify every row below.

Related: [overview](README.md), [tool catalog](07-mcp-tool-catalog.md), [shared access and safety](06-access-control-and-write-safety-prd.md).

## Fixtures and environments

- Supported WordPress 6.9+ with a verified compatible adapter and Directorist; test the release's minimum and current supported runtime combination. Include an older WordPress/missing/incompatible adapter case to prove graceful unavailability.
- Administrator; editor; listing owners A/B; custom role with listing creation/edit but no publication; custom taxonomy manager; authenticated account with WordPress `read` only; anonymous/invalid/revoked credentials. Record actual capabilities rather than relying on fixture role names.
- Two directories plus a disposable empty non-default directory; separate single-directory mode fixture. Use builder forms with presets, custom fields, conditional dependencies, mandatory fields and an unsupported extension widget.
- Own/others draft, pending, published, private, trash and expired listings; restricted contact/custom fields; attachments with allowed/denied access; site configuration with trash disabled; plan/featured/expiration constraints where native features are available.
- Hierarchical category/location trees, flat tags, shared directory associations, legacy association metadata, children, unused terms and dependencies on draft/private/trash listings.
- Controlled test extension with explicit registered and unregistered fields, sensitive fields, additional capability, invalid values and two storage adapters. Tests must not imply every installed commercial extension was audited.
- Two independent clients/users, trusted HTTPS, non-root WordPress REST URLs, controlled request failure/timeout and parallel-request injection. Use a controlled payment/refund sandbox or fake provider for the added financial workflows; no real charges or refunds.

Create/modify fixtures only in an isolated test site during implementation QA. This documentation update created no runtime fixtures and ran no payment/provider operation.

Additional fixtures: purchasers A/B, an order-only customer with no listing capability, staff/custom roles with native administration allowed/denied, supported legacy/current order storage, pending/paid/partially refunded orders, multiple currencies/precisions, receipt duplication, pending refund reservations and provider timeouts/webhooks. Use a controlled extension with read/write tools, settings/widget/domain adapters, extra permission rules, compatible/incompatible API versions, additional transactional/nontransactional storage and external-effect reconciliation.

Dashboard fixtures for [PRD 12](12-dashboard-data-prd.md): native site/own scopes, separate blogs, finite/never-expiring listings, restricted favorites, missing/partial analytics history, timezone/DST boundaries, zero-baseline comparisons, mixed/unknown currencies, migrated order duplicates, unavailable optional sources, stale/warm caches, dismissed setup and registered read-only dashboard contributions. Focused dashboard runtime checks are now recorded in the implementation guide; remaining matrix cases require individual evidence.

Site Health fixtures for [PRD 13](13-site-health-info-prd.md): roles with either/both manage_options and view_site_health_checks, multisite site/network actors, distinct CLI/web environments, private value/debug fields, unflagged secret/path-bearing fields, native layout variants, absent/stale update observations, large component inventories and explicitly registered diagnostic sections. Instrument SQL writes, HTTP/DNS requests, filesystem operations, cache content and collector invocation; focused runtime checks are recorded separately; remaining matrix cases require individual evidence.
